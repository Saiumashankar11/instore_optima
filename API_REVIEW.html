.NET Web API — Senior Architect Code Review

InStore Optima · ASP.NET Core 8 · Clean Architecture (Domain / Application / Infrastructure / Api)

High Medium Low

Summary

A mature, layered Web API with genuinely good cross-cutting infrastructure: a global exception middleware with a standard error envelope, Serilog logging, an audit interceptor, and EF Core migrations. The biggest gaps are committed secrets / weak JWT key, business logic living inside repositories, no pagination on list endpoints, swallowed exceptions, and no tests. Layering is mostly clean but inconsistent in a few places.

Key Findings

  • High Secrets committed in appsettings.json (SMTP password, hardcoded JWT key) — JWT key is a weak literal.
  • High No automated tests (no unit/integration projects).
  • Medium Business logic inside repositories — PaymentRepository creates invoices/receipts and mutates order status.
  • Medium List endpoints (GetAll*) return entire tables — no pagination/filtering.
  • Medium Swallowed exceptions (catch {}) hide invoice/receipt/order-update failures.
  • Medium Inconsistent layering: duplicate DI registrations; controllers using AppDbContext directly (BadgeController, LiveController).

Detailed Review

Architecture

  • Low Proper 4-project split with Domain interfaces and Infrastructure implementations. 👍
  • Medium Missing an application/service layer — domain workflows (payment → invoice → receipt → order status) sit in the repository, so data access and business rules are entangled.
  • Medium Namespace/folder mismatch (e.g. a repo under Infrastructure/Repositories declared in an Api.Repositories namespace) — confuses the dependency direction.

API Design

  • Low RESTful routes, DTOs at the boundary, sensible status codes. 👍
  • Medium Some endpoints return raw strings (BadRequest("Status is required")) instead of the standard error envelope — inconsistent client parsing.
  • Low No API versioning or pagination contracts; add before external consumers depend on it.

Code Quality

  • Medium Duplicate DI registrations in Program.cs (e.g. IUserRepository, IAuditLogRepository registered twice).
  • Low 17 XML-comment build warnings (CS1587) — comments on non-doc elements; clean up or suppress.
  • Low Nullable-reference warnings (CS8618/CS8620) on entities — annotate or add required.

Performance

  • Medium GetAll* with no paging will degrade as orders/products/payments grow; add skip/take + server-side filtering.
  • Low Good use of CountAsync for badges (DB-side aggregation) and AsNoTracking on reads. 👍
  • Low CancellationToken not threaded into EF queries — pass it from actions for request cancellation.

Security

  • High JWT signing key is a hardcoded literal in appsettings.json and committed — move to secrets/env and rotate; it's effectively public in git history.
  • High SMTP credentials were committed (now moved to user-secrets — rotate the old app-password, it remains in history).
  • Low EF Core LINQ everywhere → parameterized queries, no SQL injection surface. 👍
  • Low [Authorize] + role checks + inactive-user middleware present; verify a restrictive CORS policy for prod.

Error Handling & Logging

  • Low GlobalExceptionHandlingMiddleware + typed exceptions + ErrorResponseDto envelope + Serilog + audit interceptor — excellent foundation. 👍
  • Medium "Best-effort" catch {} in PaymentRepository silently drops failures (invoice/receipt/order updates) — log at minimum, ideally wrap in a transaction.

Data Access

  • Medium Multi-entity operations (payment + invoice + receipt + order) use sequential SaveChangesAsync calls without a transaction — partial writes possible on failure.
  • Medium "One payment per order" enforced via AnyAsync-then-insert (race condition) — back it with a unique DB constraint.
  • Low Repository pattern + migrations are consistent and readable. 👍

Dependency Injection

  • Low Interfaces resolved to implementations with correct scoped lifetimes; new email transport wired cleanly (Brevo with SMTP fallback). 👍
  • Medium Duplicate/commented-out registrations clutter Program.cs — consolidate into extension methods (AddInfrastructure()).
  • Medium Controllers bypassing repositories with direct AppDbContext break the abstraction in spots.

Testing

  • High No test projects. Add xUnit unit tests for repositories/services (EF InMemory or SQLite) and WebApplicationFactory integration tests for auth + payment flows.

Recommendations

  1. Move JWT key + all secrets to user-secrets/env vars; rotate anything already committed.
  2. Introduce an Application service layer; move payment/invoice/order workflows out of repositories.
  3. Wrap multi-entity writes in IDbContextTransaction; stop swallowing exceptions.
  4. Add pagination + server-side filtering to all list endpoints; add a dashboard summary endpoint.
  5. Add a unique index for one-payment-per-order; thread CancellationToken into EF calls.
  6. Consolidate DI into AddInfrastructure()/AddApplication() extensions; remove duplicates.
  7. Stand up xUnit + integration tests; wire into CI.

Strengths

  • Clean Architecture layering with clear Domain interfaces.
  • First-class cross-cutting concerns: global exception handling, standard error envelope, Serilog, audit interceptor.
  • EF Core best practices in reads (AsNoTracking, CountAsync aggregates) and parameterized queries.
  • Thoughtful domain automation (auto-invoice/receipt, badge counts, PO notifications) and resilient email (HTTPS + SMTP fallback).

Final Verdict

Strong B / B+ API. The infrastructure (logging, error handling, layering) is above-average for a project this size. The blocking items for production are secret management + JWT key, transactional integrity for multi-entity writes, and a test suite. Refactoring business logic out of repositories and adding pagination are the next tier — important for maintainability and scale, but not emergencies.
